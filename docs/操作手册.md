# 自媒体中台操作手册

## 一、发布新版本

1. 确认 GitHub `master` 分支的 `Media CI` 已通过。
2. 在 CI/CD 中台选择自媒体中台项目。
3. 选择 `deploy`，确认 CPU、内存、端口和绑定地址。
4. 点击发布，等待 `Deploy Media Platform` 全部步骤变绿。
5. 打开 `/api/health`，确认返回 HTTP 200，再测试登录和首页数据。

默认部署位置为 `/opt/media-platform`，发布版本位于 `releases`，数据库数据卷不会随版本替换而删除。

## 二、SSH 主机身份变更告警

### 现象

流水线在上传发布包时失败，日志包含：

```text
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!
Host key verification failed.
```

这是 SSH 的安全保护：当前服务器返回的主机公钥与 GitHub Secret `DEPLOY_HOST_KEY` 中固定保存的公钥不一致。常见原因包括：

- 公网 IP 更换，但 `DEPLOY_HOST` 或 `DEPLOY_HOST_KEY` 没有同步更新；
- 服务器重装、系统镜像更换或 SSH 主机密钥重新生成；
- 同一个公网 IP 被分配给了另一台实例；
- 极少数情况下可能存在网络劫持，因此不能直接关闭严格校验。

### 安全处置步骤

1. 在阿里云控制台核对目标实例、公网 IP、安全组和 SSH 端口。
2. 优先通过阿里云 Workbench 或实例控制台执行：

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256
```

3. 在可信电脑从公网读取公钥并计算指纹：

```bash
ssh-keyscan -T 10 -p 22 -t ed25519,rsa <服务器公网IP> > server-known-hosts
ssh-keygen -lf server-known-hosts -E sha256
```

4. 只有控制台指纹、公网扫描指纹和部署日志中的新指纹一致时，才能更新密钥。
5. 更新 GitHub 仓库或 CI/CD 中台中的配置：

   - `DEPLOY_HOST`：最新公网 IP、稳定域名，或已接入工作流的 Tailscale IP；
   - `DEPLOY_PORT`：实际 SSH 端口；
   - `DEPLOY_HOST_KEY`：`ssh-keyscan` 输出的完整公钥行；
   - `DEPLOY_USER`、`DEPLOY_SSH_KEY` 通常无需因 IP 变化而修改。

使用 GitHub CLI 更新示例：

```bash
ssh-keyscan -T 10 -p 22 -t ed25519,rsa <服务器公网IP> | \
  gh secret set DEPLOY_HOST_KEY --repo qiubo-master/Media
```

如果公网 IP 也变化：

```bash
printf '%s' '<新公网IP>' | gh secret set DEPLOY_HOST --repo qiubo-master/Media
```

6. 重新执行部署流水线，并检查 `/api/health`。

### 禁止的临时处理

不要在流水线中使用以下方式绕过告警：

```text
StrictHostKeyChecking=no
UserKnownHostsFile=/dev/null
只删除 known_hosts 后直接重试
```

这些做法会失去对目标服务器身份的验证。正确方法是先通过云控制台核对指纹，再更新固定主机公钥。

## 三、部署后检查

```bash
curl -i http://<服务器地址>:8080/api/health
```

检查项：

- HTTP 状态为 200；
- PostgreSQL、应用和 Nginx 容器健康；
- 登录后会话正常；
- 账号矩阵、作品数据和首页看板可以读取；
- 数据库迁移已执行，旧数据仍在。

## 四、回滚

在部署工作流中选择 `rollback`。回滚只切换应用发布版本，不回滚或删除 PostgreSQL 数据。涉及不可逆数据库变更时，应先制作数据库备份并单独制定回退方案。

## 五、更换实例后提示 Permission denied (publickey)

主机指纹校验通过后，如果发布日志继续提示：

```text
Permission denied (publickey)
```

说明目标实例没有保存与 GitHub Secret `DEPLOY_SSH_KEY` 对应的公钥。常见于重装系统、更换实例或重建 root 用户的 `.ssh` 目录。

安全恢复步骤：

1. 为该项目单独生成一套 Ed25519 部署密钥，不要与个人登录密钥共用。
2. 将私钥完整保存到 GitHub Secret `DEPLOY_SSH_KEY`，不要提交到仓库。
3. 通过阿里云云助手或 Workbench，把对应公钥追加到部署用户的 `~/.ssh/authorized_keys`。
4. 确保目录权限为 `700`、文件权限为 `600`。
5. 先使用新密钥执行一次只读 SSH 登录测试，再重新运行发布流程。
6. 删除本地临时私钥；保留 GitHub Secret，不在聊天、日志或工单中粘贴私钥。

以 root 部署用户为例，云助手命令格式如下：

```bash
umask 077
mkdir -p /root/.ssh
touch /root/.ssh/authorized_keys
grep -qxF '<项目部署公钥>' /root/.ssh/authorized_keys || echo '<项目部署公钥>' >> /root/.ssh/authorized_keys
chmod 700 /root/.ssh
chmod 600 /root/.ssh/authorized_keys
```
